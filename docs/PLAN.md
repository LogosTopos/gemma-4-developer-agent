# 不跑重训练能做什么

> 前提：本机 M4 / 24GB / macOS，无 NVIDIA GPU。跑不了 4×L4 上的 Gemma-4-31B 推理，
> 更谈不上微调 31B。但**这个竞赛的得分点本来就不在训练上**——下面逐条说明。

## 关键判断：为什么"不训练"几乎不损失什么

1. **提交物里根本没有可训练的位置**。只能交 YAML + prompt + 采样参数（+ 可选 LoRA）。
   所有"逻辑"都必须表达为**文本与结构**。所以主要杠杆是 prompt 工程与 Agent 架构。
2. **排行榜极低**。57 队，榜首 **0.12**，大多数 0.00–0.06。
   这说明**能把任务跑通、拿到任意非零分就已经在头部附近**。
   先把 pipeline 打通的价值远大于抠模型。
3. **任务本身是小切口**。129 个任务里 **40% 的金标 patch 不到 20 行**，63% 不到 50 行，
   改动文件数中位数为 **1**。难点不在代码量。
4. **真正的瓶颈是"定位"**：**78% 的问题描述里没有任何文件路径**，
   只有 22% 提到文件名、15% 含报错信息、47% 含反引号包裹的符号名。
   → 任务本质是「从一段简短 PR 描述，在陌生仓库里找到那 1 个文件的那 30 行」。
   这正好是 **prompt 策略 + 检索工具 + 上下文管理** 能大幅改善的地方。

## 分层行动方案（按性价比排序）

### L0 · 本地可做，零 GPU，立刻能做

| 事项 | 价值 | 状态 |
| :--- | :--- | :--- |
| **修复 graph/embedding 的 0 字节数据** | 否则 3 个代码智能工具静默失效 | ✅ 已完成（`scripts/repair_links.py`，修复 258 个） |
| **解包仓库快照，做真实的代码地形分析** | 知道要改的文件长什么样、在哪一层 | 待做（快照下载中） |
| **金标 patch 挖掘**：统计"改哪个文件、什么类型的改动" | 反推 prompt 该引导 Agent 关注什么 | 部分完成（见 README 统计） |
| **提交包静态校验**：YAML 编译 + 全部硬闸门检查 | 提交被拒 = 0 分，必须提前拦住 | 待做 |
| **本地装纯 Python 包**（swegemma/adk-*/google-adk） | 能读源码、能跑 YAML 编译、能跑校验 | 待做 |
| **用金标 patch 自建"回放"验证器** | 验证我们的 verify 逻辑对不对，不依赖模型 | 待做 |

### L1 · 用免费 GPU 跑真实评测（关键突破口）

**核心事实（源码分析确认）**：`swegemma` 的 `--sandbox subprocess` 是官方支持的 Docker 替代，
且 `models/registry.py` **不强制本地 vLLM**——它只是 `LiteLlm` 的 OpenAI 兼容 HTTP 客户端。

→ 意味着我们可以在 **Kaggle Notebook 的免费 GPU**（T4×2 / P100）上：
- 装 wheelhouse 里的纯 Python 包（`swegemma` / `adk-*` / `google-adk` 都是 py3-none-any）
- 用 `--sandbox subprocess` 跑真实的 129 个任务
- 模型侧二选一：
  - **(a) 跑小号 Gemma**（`gemma-4-12b-it` 或 `gemma-4-e4b-it`）配 vLLM，
    当作 31B 的**代理模型**。绝对分数不等于官方，但**能比较两个 prompt / 架构的优劣**。
  - **(b) 接远程 OpenAI 兼容 API**（环境变量 `OPENAI_BASE_URL` + `OPENAI_API_KEY`，
    注入点 `swegemma/models/registry.py:94-110`）。

这一步的价值：**把"猜"变成"测"**。哪怕代理模型只有 5% 通过率，
它的**相对排序**足以指导 prompt 迭代。

⚠️ 注意：代理模型只用于**本地开发迭代**。最终提交必须用 Gemma 基座（单模型规则）。
另需确认竞赛规则是否允许用外部 API 做开发期评测（见讨论区 742807 的蒸馏澄清，主办方尚未答复）。

### L2 · 真正的工作量所在：Agent 架构与 Prompt

这是**不需要训练**、但决定成败的部分：

1. **Prompt 策略**
   - 问题描述 78% 无路径 → 需要一套「从错误信息/符号名反推文件位置」的固定流程
   - 引导使用 `search_similar_code`（注意：它**只能接受符号名**，
     传自然语言会静默返回空结果——这是个必须写进 prompt 的坑）
   - 针对 async 代码路径（图里完全没有 async 节点）的退路：直接用 `read_file` / `grep`
   - 严格约束：不改测试文件、不跑全量测试、scratch 脚本放 `/tmp`

2. **Agent 架构**
   - `AgentTool` 子代理隔离上下文（探索型子代理只读，把噪声挡在主 Agent 之外）
   - 定位 → 分析 → 编辑 → 验证 的分阶段流转
   - 何时 `submit_patch`（它免费且结束会话，必须作为最后一步）

3. **采样参数**
   - `thinking_budget` 与 `max_output_tokens` 的取舍：
     32k 上下文是硬顶，思考太长会把 tool call 挤断（触发 nudge，浪费轮次）
   - `eval_config.yaml` 里的默认值（1 分钟 / 10 次工具调用）是**样例占位**，
     swegemma 根本不读这个文件——别被它误导

4. **多轮抗错**
   - `edit_file` 三层匹配的行为（exact 多重匹配会**直接失败不降级**）
   - 超时但已有 diff 时 harness 仍会进 Phase 2 → 尽早产生「有点对的改动」比追求完美更划算

### L3 · 可选：LoRA 微调

只有在 L2 做完、拿到稳定的本地评测基线之后才值得考虑。
成本：租 GPU 微调 31B 的 LoRA（r=16 约 110–220MB）。
收益：不确定，且**不是当前的瓶颈**。
→ **建议先不做。**

## 建议的执行顺序

```
1. [进行中] 下载 129 个仓库快照 (20GB)
2. 本地装纯 Python 包，跑通 submission 静态校验
3. 解包 3–5 个快照做代码地形分析，产出「定位策略」假设
4. 写第一版 submission（prompt + agent.yaml）
5. 上 Kaggle 免费 GPU，用 subprocess sandbox + 小号 Gemma 跑 10 个任务的 A/B
6. 依据相对结果迭代 prompt，逐步扩到全部 129 任务
7. 用目标基座（31B）做最终验证并提交
```
