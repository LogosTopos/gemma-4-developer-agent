# 数据集价值、本地工具实验与 LoRA 训练准备

更新日期：2026-09-28。本文整理已经完成的调查与本地实验，供接手者决策和执行；没有新增数据审计、GPU 实验或训练。后文明确区分已验证结果、工程估算和待实现方案。文中不附原始参考补丁、测试补丁或凭据。

## 1. 这 20 GB 多的数据是用来做什么的

它是一个带参考修复和验证测试的仓库修复开发集，不是同等体积的独立指令训练数据。每个任务让 Agent 根据问题描述操作一个修改前的 Python 仓库，最终提交工作树补丁。代码、测试与图用于理解仓库；参考 patch 和 test_patch 用于监督构造及独立评测。

官方数据说明将这 129 条定义为公开训练/开发任务，允许本地 Agent 开发、提示词编制和离线验证。评分时替换为隐藏测试集；截至本次调查，页面称隐藏集约 120 条，公开/私有评分部分大致各半，任务来自私有仓库。这不是隐藏集精确题数的本地核验，也不支持把社区推算的 58 道 public 题当成已确认事实。[官方数据说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/data)

### 每类资产可以提供什么

| 资产 | 已有信息 | 对我们的直接价值 |
|---|---|---|
| problem_statement、hints_text | 用户需求；本批 hints 全空 | 模型输入、检索查询、需求信息量分组 |
| 修改前工作树 | 实际源码、既有测试、配置与 API 约定 | 定位、上下文选择、补丁生成、测试选择 |
| reference patch | 一种可供参考的实现及修改位置 | 定位标签、before/after 编辑监督、离线诊断 |
| test_patch | 评分阶段加入的验证测试 | 独立 fail-to-pass 验证、训练部分行为归纳 |
| AST 图 | 符号与结构关系 | 查询符号邻居、补充依赖/调用上下文 |
| 256 维节点向量 | 已有符号的向量 | 符号相似性实验，不等于可用的自然语言编码器 |
| wheels、Docker、setup、harness | 依赖准备和验证流程 | 构造可复现实验、区分环境失败与修复失败 |

没有现成的 Agent 工具调用轨迹、真实模型推理轨迹或自主成功 rollouts。不能直接把 reference patch 改写成一段虚构的成功对话，再称其为真实 Agent 经验。最终评分看修复行为，参考 patch 只是一个解法，逐字匹配它不是唯一正确标准。

## 2. 已知数据问题与使用边界

1. **归档与提交标识存在不一致。**检查的 12 个快照归档 HEAD 均不等于声明的 base_commit；进一步检查 Requests、HTTPX 的两个快照，声明 commit 对象不存在，而目标文件与归档 HEAD 一致。参考 patch 可应用于归档工作树。实验应绑定快照哈希和实际文件，不能直接 `git checkout base_commit` 假设还原成功。原因尚未确定。
2. **输入信息量不均。**一些描述直接指出修复方法，一些只有标题或 issue 链接，另一些主要是 PR 模板。53 条短描述不是 53 条不可解任务，但应单独观察。增加 prompt 长度不能补出缺失的需求。
3. **图不是源码的完整替代。**所有 129 个图都可解析，元数据与声明任务一致；节点键与 NPZ 键一致。但全批图没有独立的 `async def` 定义节点，异步逻辑仍须检索源码。
4. **别名不是额外样本。**按任务 ID 与 commit 命名的图/向量文件逐个 SHA-256 比对一致；256 个文件对应 127 个提交组及其任务别名，不应当作 256 份独立训练数据。
5. **向量检查范围有限。**12 个实验样本的全部向量是 256 维、有限且非零；其余样本未逐向量做数值检查。现有 `embedding_utils.embed()` 实测接受符号键/后缀，普通自然语言句子可能返回空；不能假设已经提供任意 issue 的 query embedding。
6. **图工具并非强制路线。**比赛提供图以辅助探索，不要求 Agent 每题必须调用图。我们的 v4 使用源码检索；本轮实验的图扩展没有带来更好的整体折中，因此没有装入最终候选。不能把“有资产”变成“必须使用”的架构要求。
7. **本地局部测试不同于官方评分。**已跑的 Requests、Rich 参考修复检查关闭了部分 conftest/自动插件；FastAPI 检查直接调用目标函数。本机 Python 3.14.6 与官方沙箱版本不同。局部 before-fail/after-pass 证明相应行为，不证明完整任务通过。

公开数据生成流程的说明与本地实测应分别保留。官方描述了筛选与验证标准，但我们确实看到信息不足的描述和归档标识问题；不能用官方流程文字替代实际质量检查，也不应把局部异常外推为隐藏集全部失效。

## 3. 数据拆分、去重与标签隔离

现有实验先按仓库分为 FastAPI/Rich 开发部分 115 条、Requests 13 条、HTTPX 1 条。v4 又按 repo + base_commit 的确定性哈希，将前 115 条分为 82 条选择配置、33 条选定后检查；相同提交组不跨组。Requests/HTTPX 作为额外仓库诊断。

这些不是全新盲测：v3 开发接触过 FastAPI/Rich，早期数据准备也检查过部分 Requests/HTTPX 标签。HTTPX 只有一条，不能估计泛化率。后续继续反复根据同一保留集改方法，应把它重新标为开发集，而不是沿用“独立验证”措辞。

后续数据生产应遵循以下顺序：

1. 保留任务 ID、repo、声明 commit、快照/源文件哈希、数据版本等来源字段。
2. 以任务/提交组为最小单位划分；根据相同或近重复的 issue、补丁家族、目标函数及相邻版本进一步检查跨组重复。
3. 在划分之后切函数、代码块、编辑样本和排序正负例。同一任务的派生样本不得跨组。
4. 训练部分可以用 gold 作为监督输出；正常 Agent 输入只能有该题问题和修改前工作树，不能混入答案路径、参考补丁或新增验证测试。
5. 单独的评测进程持有 test_patch，负责应用候选 patch 和评分；不要把整个原数据目录或 evaluator 目录挂载到 Agent 沙箱。

目录命名隔离不是操作系统权限隔离。已有 `agent/` 与 `evaluator/` 分离是数据使用约定，还需要运行时挂载边界。按参考修改位置截取的 oracle 上下文只能用于离线瓶颈诊断；不能和正常检索成绩混报。

## 4. M4、24 GB 统一内存可以做的事情

这些是适合现有本机的处理方向，不表示全部已经实现。复用现有提取与审计结果，避免再次全量解压或重复扫描 20 GB。源码分析不需要执行仓库代码。

| 工作 | 本地实施方式 | 产物与验收 |
|---|---|---|
| 源码内容去重 | 文件/函数哈希，单仓流式处理，增量缓存 | 紧凑语料与来源索引；不破坏任务版本 |
| 结构特征 | AST、异步符号、imports、调用点、测试引用 | 统一上下文索引；记录解析失败与覆盖范围 |
| 轻量排序训练 | BM25/精确标识符/路径角色/结构特征；正则化线性或小树模型 | 小权重推理，不新增 LLM 调用；按任务组验证 |
| 测试选择 | 既有测试与代码引用、配置解析、时间上限 | 少量相关测试，环境错误与断言失败分开 |
| 安全编辑回放 | 唯一匹配、编辑、语法检查、差异审查、局部测试 | 精确编辑接口及结构化结果 |
| SFT 数据编译 | 格式化、分组去重、tokenize、截断/模板检查 | 可追溯 JSONL 和长度分布，供 GPU 后续训练 |
| 轨迹筛选 | 实际工具日志、补丁、测试结果关联 | 成功、失败和 oracle-assisted 类型清晰区分 |

已经从 127 个提交组提取了完整 Python 源码语料供定位实验使用；不要重新按答案文件列表抽取输入，那会使定位实验泄漏。当前定位器仅覆盖 Python；非 Python 配置或新文件任务需单列处理。

可先训练一个小型非神经排序器，把权重导出到脚本；没有必要为此先训练神经 embedding 模型。候选对数量很大不代表独立监督很多，129 个 issue 足以让复杂排序器过拟合。额外神经检索模型的比赛许可也尚需明确。

24 GB 统一内存不是 24 GB 独占 CUDA 显存，系统、进程、缓存共用它。本机不应作为指定 31B 模型 LoRA 训练的默认方案；即使某种 offload 能启动，也没有本次实测支持其吞吐、训练稳定性或比赛兼容性。

## 5. 从已有结果改善 prompt 和 skill

方向是维持一个 Agent，把可确定执行的工作放进用途明确的工具抽象。系统提示只保留固定工作流、权限边界、预算与完成条件，不逐案例追加搜索规则。

v4 已完成三轮、19 种定位配置比较。训练部分 Hit@5 为 68/81，选定后检查的 33 条为 28/33；v3 对应为 61/81、26/33。验证部分文件 Recall@5 为 74.6%，说明“至少找到一个文件”远不等于找全修改位置。HTTPX 的 7 个参考文件只覆盖 4 个，也是多文件上下文仍不足的证据。

v4 验证部分检索耗时中位数约 0.637 秒，返回字符中位数约 3590；计时从已加载源码建索引开始，不含磁盘扫描和进程启动。主提示和 skill 说明约 336 个英文词。它们衡量检索成本与材料长度，不直接证明模型思考量或端到端解题率。

| 证据/问题 | 应优先改的工具行为 | 不应采取的替代做法 |
|---|---|---|
| async、长函数、模块尾部曾漏检 | 保持 v4 的源码/窗口覆盖 | 再向 prompt 堆搜索技巧 |
| 找到一文件但缺调用者或接口关联 | 有界补充引用、完整函数及相关测试 | 无限制增加 top-k 或图邻居 |
| 短描述只有标题/链接 | 返回可用证据与覆盖不足标记 | 编造缺失需求或重复改写同一查询 |
| 小修改占多数 | 唯一匹配编辑、语法检查、短 diff 摘要 | 让模型每次临时写复杂 shell/Python |
| 测试经常受环境影响 | 解析配置、选相关测试、超时与错误分类 | 自动修复无关依赖或误报测试通过 |
| 模型容易耗在工具编排 | 一个 skill 包的固定 context/edit/verify 操作 | 多个用途重叠、需模型自行选择的 skill |

其中 context 已有候选实现；edit/verify 事务抽象及上下文覆盖新指标仍待实现。编辑工具可以检查前置条件、应用修改、验证并摘要，但语义修复本身仍需模型提出。低检索分数不能未经校准就解释为任务不可解。

本地回放使用预编写模型响应，因此不能用它归因线上失败。下一次有真实 Gemma 环境时，应记录首次编辑时间、模型/工具 token、工具错误、定位覆盖、补丁有效性、相关测试、终止原因，并按定位/理解/编辑/环境/超时区分失败。

## 6. LoRA：许可和量化路线必须分开判断

### 2026-09-28 主办方更新

Ryan Holbrook 在 9 月 28 日答复：LoRA 加载修复已于前一天应用；允许使用 gemma-4-31b 自生成数据训练；使用其他模型输出的问题仍待答复。因此“LoRA 加载是否已修复尚未确认”已经过期，应替换为“主办方已宣布修复，我们尚未实测 adapter 加载”。这也不是对所有其他教师蒸馏方式的许可。[主办方答复 743964](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743964)

允许上传 adapter 不等于任意量化训练方案与评分加载器兼容。比赛推理指定 `gemma-4-31b-it-qat-w4a16-ct`：QAT 描述权重来源，W4A16 描述权重/激活精度，CT 是 compressed-tensors 格式。已读取的配置为按组 INT4、group_size=32，并有未量化层的排除清单，不能按所有参数都占半字节估算。LoRA 只训练附加低秩参数；冻结基座不需要为全部 31B 参数保留优化器状态，但仍需基座权重、激活、反向传播临时内存与 adapter 状态。[Google 官方 CT checkpoint](https://huggingface.co/google/gemma-4-31B-it-qat-w4a16-ct)

### 两条可研究路线

| 路线 | 训练底座如何加载 | 优点 | 必须验证的风险 |
|---|---|---|---|
| A：以官方 CT checkpoint 为来源，反量化为 BF16 后做 LoRA | 用兼容加载链恢复冻结浮点权重，接 PEFT/等价 adapter | 尽量对齐官方量化后的权重来源，训练内核更常规 | 反量化/训练支持、内存、模块名称、导出 adapter 在原 CT 推理模型上的行为 |
| B：另用训练框架支持的 4-bit 底座做 QLoRA | 例如该框架支持的不同量化表示 | 显著降低冻结基座占用，可用较小 GPU 试验 | 它不等同于原 CT W4A16；权重/量化误差不同，adapter 转回比赛 CT 底座是否有效需实测 |

CT 推理能加载，不自动意味着可以直接通过同一打包 INT4 算子训练。已查阅的 Transformers compressed-tensors 文档说明普通路径会在第一次 forward 时解压模型；`dequantize=True` 的训练路径也不是全程保持打包 4-bit 权重。因此不能据下载大小判断训练显存。路线 A 的反量化结果不是恢复未量化原始权重；路线 B 的 NF4 或其他 4-bit 格式不能仅因同为“4-bit”就声称完全一致。不要未经验证把 adapter 合并后重新量化并当作比赛要求的原基座。[Transformers compressed-tensors 文档](https://huggingface.co/docs/transformers/main/quantization/compressed_tensors)

已检查的 Unsloth 31B notebook 加载 `unsloth/gemma-4-31B-it`，设置 `load_in_4bit=True`、`max_seq_length=8192`、`device_map="balanced"`，注明使用双 T4；没有加载比赛官方 CT checkpoint。它提供工程可行性的线索，不证明指定 CT checkpoint 在单张 T4、24 GB 卡或相同上下文长度下可训练。多卡的物理显存也不会自动变成一个连续显存池，取决于切分、通信和 offload 实现。[Unsloth 训练说明](https://unsloth.ai/docs/models/gemma-4/train)、[已检查的 31B notebook](https://www.kaggle.com/code/danielhanchen/gemma4-31b-unsloth)

### GPU 选择：估算而非 fits 保证

按约 31B 参数做量级估算，仅 BF16 权重约 62 GB（57.7 GiB）；仅 4-bit packed 权重理论值约 15.5 GB（14.4 GiB）。实际模型可能保留未量化层并有量化元数据，还需激活、KV/临时张量、adapter、梯度与优化器、框架缓存；这两个数不是训练总显存。

作为文件规模参照，已读取 Google 的 `gemma-4-31B-it-qat-q4_0-unquantized` 权重索引，`total_size=62,546,177,752` 字节，约 62.55 GB。它是另一个官方发布条目，不是我们已经验证与 W4A16 CT 逐权重相同的替代品；不能跳过兼容性核对直接换训练底座。[Google QAT unquantized 条目](https://huggingface.co/google/gemma-4-31B-it-qat-q4_0-unquantized)

| 候选硬件 | 更合适的尝试 | 实际限制 |
|---|---|---|
| 单张 24 GB CUDA 卡 | 短上下文、低 rank 的 QLoRA 探索 | 余量紧，不保证能跑；不适合作为 BF16 路线默认配置 |
| 单张 48 GB 卡（如 L40S/RTX 6000 Ada） | 训练框架支持的 4-bit QLoRA 小规模试验 | 不代表长 Agent 轨迹可训练，仍须测峰值显存 |
| 单张 A100 80 GB / H100 80 GB | 官方来源反量化后的 BF16 LoRA 短序列试验，或更宽裕的 QLoRA | BF16 权重已占主要空间，长上下文不保证 fits |
| 单张 H200 141 GB 或两张 80 GB 卡 | 为 BF16 LoRA 与较长轨迹留更多空间 | 多卡需要正确分片；不能根据显存简单保证训练吞吐 |

建议 GPU 冒烟配置先用 batch=1、约 2048 token、低 rank（例如 8/16）、gradient checkpointing，验证一次 forward/backward/optimizer step 和导出加载；再按真实样本长度增加到 4096/8192 等。梯度累积增加有效 batch，不等价于增加同时驻留序列。以上只是试验起点，本次没有运行 GPU、测得峰值显存或给出训练时长/费用保证。

租卡前优先确认精确 checkpoint、tokenizer/chat template、训练实现、量化配置、target_modules 和 adapter 前缀，避免只按“31B 4-bit”选择硬件。最长可支持上下文与我们实际训练长度是两个问题。

## 7. 如何准备可信的训练样本

优先做窄任务而非把整仓库塞进上下文：issue + 固定检索上下文 → 精确编辑/合法工具调用。另一类是实际失败工具结果 → 修正调用，以及验证结果 → 正确下一步动作。它们直接服务于少思考、少编排和可靠修改。

推荐每条训练记录至少包含：

- task_id、repo、split、输入/源文件哈希、检索器版本及数据来源。
- 实际可见的 system/user/tool 消息、工具 schema、真实调用参数和真实返回值。
- assistant 目标消息、loss mask、token 数和截断方式；通常不把工具返回文本本身当模型生成目标。
- 生成者与来源类型：真实自主 rollout、人工操作演示或 oracle-assisted 参考修复演示。
- 候选 patch 哈希、应用结果、语法检查、局部测试和官方兼容评测结果，保留失败原因与耗时。

reference patch 可作为训练部分的编辑目标；test_patch 可在隔离端检验行为。不向模型输入泄漏答案位置或隐藏测试。不要把“补丁可应用”当作“行为正确”，不要把“局部测试通过”当作“官方任务通过”，不要填造模型没有产生的思考过程。

固定未训练基线后，adapter 对照至少检查：同一输入能加载、adapter 确实生效、工具格式合法、预算相同、测试结果与耗时有改善。数据只有 129 个独立问题，多轮重复训练容易记忆；应优先增加可信的实际行为证据，而不是提高 epoch 或复制样本充数。

## 8. 给接手者的优先顺序

1. **先实现短编辑/验证抽象。**以训练部分已知编辑作真实工具回放，测唯一匹配失败、无关输出、测试启动成本；与已有 context 入口协调，保持 Agent 简单。
2. **把定位指标扩展为修复上下文覆盖。**记录完整函数、关联调用者、全部参考文件召回与 token 成本。只在训练部分选择策略，然后冻结检查保留集。
3. **建立训练数据编译和过滤流水线。**先产出少量可追溯、真实运行验证的样本与长度统计，区分 oracle 演示和自主轨迹，再决定是否租卡。
4. **获取 GPU 后先做加载与一批训练冒烟。**验证官方 CT 来源路线或明确不同量化路线，再做 adapter 导出、评分加载与小规模对照；通过后才扩大训练。

截至本文，没有真实 Gemma 本地 A/B 轨迹、LoRA 训练结果或 GPU 内存实测。定位指标和接口回放可以支持工具决策，不能代替最终解题率。
