# 2026-09-27：Gemma 4 候选包 v3

已完成本地实验与候选包，未上传 Kaggle。v2 的线上结果已核实：submission 56575713，COMPLETE，无错误信息，public score 为 0.05。当前没有比赛同款推理服务/GPU，因此没有测得 v3 的真实解题率，也没有证据保证其得分高于 0.05。

## 本次修改及依据

1. 保留单个 Gemma Agent，加入一个只读 Python 定位 skill。按函数、异步函数和类检索，结合标识符与现有测试的 import 关系，返回候选文件、行号和短片段。不增加第二次模型推理，不使用任务数据库、参考补丁或网络。
2. 定位不清楚时才调用 skill；已给出文件时直接阅读。提示词要求检查调用方和多文件影响，避免把检索排名当成修改答案。
3. 单题预算从 3 分钟/24 次工具调用/32 轮改为 4.5 分钟/40 次/64 轮；命令超时从 45 秒改为 60 秒。单次最大输出从 3072 改为 8192 token，保留 thinking，不再传 thinking_level=low。官方入门 notebook 同样明确移除了 thinking_level；这不证明 v2 的参数错误或它导致了低分。[官方 notebook](https://www.kaggle.com/code/ryanholbrook/getting-started-gemma-4-developer-agent)
4. 保留复现、针对性检查、diff 审阅、最终 submit_patch 的流程。允许任务本身要求的配置修改，禁止通过削弱测试或评分检查制造通过。

第 1 项有下面的本地定位实验支撑；第 3、4 项仍是待模型验证的设计选择。几项同时变化，未来即使分数上涨，也不能直接归因到某一项。

## 实验数据与隔离

从本地 129 个任务对应的原始快照读取 Python 文件，得到 127 组仓库/提交的源码语料。两个共享提交组的 Python 文件已逐文件确认相同后复用。没有执行仓库代码，也没有用参考补丁先筛选候选文件。

检索输入只有 problem_statement 和快照中现有 Python 源码（包括现有测试）；patch 只用于最后计算命中指标，test_patch 不进入检索。原始文件和原始数据目录未修改。

开发集为 FastAPI 67 题、Rich 48 题。比较三种新变体后，按开发集选择 imports 变体并冻结，再运行 Requests 13 题、HTTPX 1 题。后者是按仓库留出的诊断集，不应称为从未接触的盲测：早先数据准备已看过其中部分任务，而且样本很小。

指标只计算参考补丁涉及的、快照中已存在的、非测试 Python 文件。开发集有 1 题没有此类目标，因此分母是 114，留出集分母为 14。新建文件、非 Python 变更不由该指标评估。

## 定位结果

Hit@k 表示前 k 个生产代码候选中至少包含一个参考修改文件，不表示找全所有文件，更不表示修复成功。旧基线是 9 月 26 日的确定性文件检索程序，**不是 v2 模型运行时实际的定位表现**。

| 开发集方法 | Hit@1 | Hit@3 | Hit@5 | Hit@10 | 文件召回率@5¹ |
|---|---:|---:|---:|---:|---:|
| 旧文件检索 | 21.9% | 39.5% | 52.6% | 69.3% | 44.5% |
| 函数级词项检索 | 36.8% | 62.3% | 70.2% | 78.9% | 59.7% |
| 加标识符与路径权重 | 38.6% | 66.7% | 74.6% | 81.6% | 62.5% |
| 再加现有测试 import 关系（选用） | 42.1% | 68.4% | **76.3%** | 82.5% | 64.8% |

¹ 每题目标文件召回率的平均值。开发集 Hit@5 从 60/114 增至 87/114：30 题新增命中，3 题丢失命中，57 题两者都命中，24 题都未命中。存在明确退步，不能把新工具当成可靠答案来源。

| 留出集方法 | Hit@1 | Hit@3 | Hit@5 | 文件召回率@5 |
|---|---:|---:|---:|---:|
| 旧文件检索 | 11/14 | 12/14 | 14/14 | 90.8% |
| 冻结的新定位器 | 12/14 | 13/14 | 14/14 | 93.4% |

HTTPX 唯一一题的文件召回率@5 从 5/7 降至 4/7；Requests 的改善不能掩盖这一退步。针对多文件任务，仍需要模型阅读调用关系并继续搜索。

新定位器开发集耗时中位数约 0.60 秒，留出集约 0.084 秒，包括内存中的 AST 建索引与排名，不包括解压和磁盘读取。在真实 ADK skill 回放中，读取 1252 个 Python 文件并定位约用 0.71 秒；均为本机结果，不代表 Kaggle 时延。

所有变体一次比较，没有在留出结果出来后修改排名逻辑。选择记录及冻结 SHA256 见 selection.json；dev/heldout 的逐题结果和汇总均在本目录。开发集记录的源码 hash 与最终 hash 不同，只因最终将 API/CLI 默认变体由 symbol 改为已选的 imports，排名函数实现未变。

## 运行检查

- 官方分发库的目录规则、模型声明、YAML/参数约束和 ADK 编译通过。打包目录只包含 6 个预期文件。
- 4 项定位器检查通过：异步函数和同名符号、无源码执行及语法错误容错、测试单独列出及 import 关联、只读扫描/忽略符号链接/输出上限。
- 用脚本响应模拟模型，实际运行 ADK Runner → LiteLlm → skill sandbox executor → swegemma 工具。定位器找到 fastapi/security/utils.py；预设修复前断言失败，修复后三条断言通过，submit_patch 提取 402 字节补丁，且没有遗留执行器临时文件。
- 请求实际转发 max_completion_tokens=8192、enable_thinking=true，无 reasoning_effort 参数。回放使用本地 SubprocessManager，脚本参数显式传本地 workspace 路径；提交环境默认 /workspace。

回放的模型响应和修改内容是预先编写的，**只验证接口与执行链路，不验证 Gemma 能自行决定这些操作**。本地已有库版本与评分端也可能存在差异。

## 算力问题的重新判断

主办方 9 月 26 日表示，部分提交出现 CPU/GPU/TPU 资源不可用错误是平台侧故障，并认为已修复、计划重跑受影响提交。因此不能把 v2 能评分归功于我们压缩了单题预算。[主办方说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743683)

另一方面，评测任务按顺序运行，共享 12 小时总限制。主办方确认 scorer 读取 timeout_seconds、max_tool_calls、max_time_minutes、max_turns 四个字段；当时达到总限制仍会报错，未完成任务改计零分只是计划，不能假定已上线。[预算说明](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743063)

v3 的 4.5 分钟是单题保险预算，不是全局安全证明。规划上需满足：模型启动开销 + 各任务沙箱准备时间 + 各题 Agent 耗时 < 720 分钟。例如 100 题都耗尽预算，Agent 部分约 450 分钟；150 题则约 675 分钟，剩余空间很小。官方实际任务数、准备耗时和中断粒度未经本地核实，所以无法保证不再发生总时限错误。

自定义 Python 工具通过 skill 脚本接入是主办方明确支持的路径；已按此方式实现并验证。[自定义工具答复](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743573)

## 下一次有推理资源时

先在同一组任务上比较原 v2 与 v3：记录有效补丁率、真实测试通过率、首次有效修改时间、总时长和 token 消耗；再区分定位器与预算变化的影响。优先检查本次 3 个定位退步案例，以及 HTTPX 多文件覆盖不足。获得这类结果前，v3 应视为有局部实验证据的候选，而不是已证明高分的提交。
