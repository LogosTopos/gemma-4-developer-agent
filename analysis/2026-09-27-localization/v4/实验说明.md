# v4：把定位工作放进工具，保持单 Agent

已完成三轮低成本检索实验、独立于筛选缓存的最终运行和候选包验证。没有启动模型推理服务，没有上传 Kaggle，也没有新的比赛分数。

可以把确定性的搜索、排名、代码片段选择和输出裁剪放到工具内部，让 Agent 用一个固定入口取得阅读材料。此次保留单 Agent，没有加入规划器、检索 Agent 或额外模型调用。业务语义和正确补丁仍需模型判断；定位命中率不能替代真实解题率。

## 最终结果

Hit@5 指前五个候选文件至少命中一个参考修改文件，不表示找全全部文件，也不表示代码片段已覆盖完整修复逻辑。

|---|---:|---:|---:|---:|

进步并非没有退步：训练部分新增命中 8 题、丢失 1 题（rich_3063）；验证部分新增命中 3 题、丢失 1 题（rich_3468）。HTTPX 只有一题，仍只能覆盖其 7 个参考修改文件中的 4 个。验证结果出来后未继续调参。

## 三轮实验做了什么

按 repo + base_commit 的 SHA256 固定划分原 FastAPI/Rich 开发数据：82 题用于本轮选择，33 题在选定后检查。同一提交组不跨组。Requests/HTTPX 另作诊断集。这些数据曾用于 v3 开发，因此都不是全新盲测；划分不能消除之前接触数据的影响。

共比较 19 种不同配置，均只用训练部分作选择：

1. 完整代码覆盖、文件与函数排名融合、精确标识符信号、目录角色权重，以及不同强度的测试/import 扩展。最佳训练 Hit@5 为 63/81。直接加强图扩展反而引入过多通用文件。
2. 增加结构信息、去除文档字符串后的代码检索、旧检索结果融合和近重复示例去重。最佳为 68/81，主要来自降低无关辅助文件和有效实现代码很少的文件排名；复杂融合未胜出。
3. 对最佳方案做去重、旧结果融合、去掉目录角色或文件检索的消融。没有更好的整体折中。保留 Hit@5 同为 68/81、首位命中更好且结构较简单的配置。

最终没有部署额外的代码检索路线、旧检索器副本、图扩展或近重复去重。多轮实验的价值也包括删掉没有收益的机制，而不是把所有尝试都装进工具。

早期筛选为节省时间缓存了输入特征。最终候选重新从原始语料计算，未读取这些缓存或旧预测；训练指标完全复现。四个预测列表仅去掉了末尾零分的凑数文件，不改变正分候选顺序。最终报告使用这次独立运行的耗时和结果，不使用早期各阶段时间相加的估计值。

## 留在工具内部的工作

- 自动去掉 issue 模板中的 checklist 行，保留之后的有效说明。
- 同时索引函数、异步函数、类和覆盖整个文件的代码窗口，补上原先长函数尾部及模块后半段的盲区。
- 在内部融合函数/窗口检索、整文件检索、精确标识符和路径信号。
- 依据请求内容与文件结构，降低无关示例、脚本以及实现内容很少的文件排名。它是软权重，文件不会被硬删除。
- 通过稀疏倒排和单词分解缓存减少重复计算；一次 AST 解析同时服务于定位和结构判断。
- 自动输出最多五个位置、短代码片段和两个现有测试路径。隐藏检索分数、策略和权重，扫描有时间/大小限制，遇到覆盖不足会返回 partial。

源码、参考 patch 与标签保持隔离：工具只接收 issue 和当前工作树，参考 patch 仅用于实验评分。没有按任务 ID、仓库名或答案路径写规则，没有训练向量模型或使用外部推理。

## Agent 接口为什么这样设计

模型侧固定调用：

```text
load_skill(skill_name="repo-context")
run_skill_script(
    skill_name="repo-context",
    file_path="scripts/context.py",
    args={"query": "issue 原文"}
)
```

只给一个用途明确的入口，不要求列举技能、阅读脚本、改写搜索词、挑选检索路线或调整 top-k。Agent 之后只负责理解代码、修改、针对性验证和提交。主提示加 skill 说明从约 828 个英文词缩短至约 336 个词；模型、单题预算和采样配置沿用 v3，减少额外变量。

现有本地官方提交库的 tool registry 不允许通过 YAML 任意注册 locate_issue 这样的 Python 工具，也没有可提交的 preload/tool_filter 配置。SkillToolset 会自动附带四个通用工具及固定说明。因此这里能省掉发现和选择步骤，但不能假称把评分端工具列表缩成了一个函数；没有修改或绕过主办方 harness。

## 验证与限制

- 官方分发库的目录规则、模型声明及 ADK 编译通过。
- 四项针对新逻辑的检查通过：checklist 后描述与长文件覆盖；异步函数、同一行 docstring/代码和错误源码；空查询及时间截止；只读扫描、符号链接和输出上限。
- 实际 ADK Runner → LiteLlm → skill executor → swegemma 工具回放通过。脚本化模型响应直接使用定位包进入预设修复流程，没有额外 read_file；修复前断言失败，修复后三条断言通过，提交工具提取 402 字节补丁。

回放使用预先编写的模型响应，只说明接口可以这样衔接，不证明真实 Gemma 会采用同样的高效行为。更短的上下文也可能省掉有用细节，必要时仍需 read_file。当前定位器聚焦 Python，不能自动解决信息不足的短标题、新建模块或非 Python 任务。

下一次真实推理应对照 v3/v4 记录解题率、定位后追加阅读次数、首次有效编辑时间、总时长和 token 数。当前有证据支持“以近似计算成本提高文件定位并减少返回材料”，尚无证据支持“比赛得分必然上涨”或“模型一定更少思考”。
